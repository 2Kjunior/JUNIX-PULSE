Fiche opératoire n° 004

Construire Junix Pulse de zéro, de l'installation à l'application actuelle

Projet : Junix Pulse · Date : 12 novembre 2026 · Suite de : FICHE 003 (construire l'APK sur l'ordinateur) · Compagnon : l'explorateur du projet
Comment lire cette fiche Les phases 0 à 10 se font en entier, à la main : chaque fichier est donné complet, chaque ligne est commentée, et ce code a été vérifié par TypeScript et par Jest avant d'être écrit ici. À la fin de la phase 10, tu as une vraie petite app : des onglets, une base de données, des rappels qu'on crée, qui sonnent et qu'on termine.
Les phases 11 à 21 suivent l'ordre dans lequel le vrai Junix Pulse a été construit. Le vrai code fait plusieurs dizaines de milliers de lignes : ces phases donnent les commandes exactes, la liste des fichiers à créer couche par couche, la recette, et un lien vers chaque vrai fichier dans l'explorateur, où tu peux lire son code.

1. Objectif

Savoir refaire, seul et sans IA, le chemin complet qui mène à Junix Pulse : installer les outils, créer un projet Expo, voir sa première page sur son téléphone avec Expo Go, construire la première fonction complète (les rappels) en respectant l'architecture du projet, puis enchaîner les autres modules jusqu'à l'application actuelle et son fichier d'installation Android (APK).

On reconnaît la réussite à trois choses :

  1. sur le téléphone, l'app d'entraînement junix-pulse-tuto affiche cinq onglets, et un rappel créé « Dans 1 h » apparaît dans la liste puis sonne à l'heure ;
  2. dans le terminal, npx jest affiche Tests: 5 passed ;
  3. tu sais dire, pour n'importe quel fichier du vrai projet, dans quelle couche il se trouve et à quoi il sert (l'explorateur t'aide).

4. Hypothèses

  • Windows 11, terminal intégré de VS Code. Les commandes sont les mêmes dans PowerShell, Invite de commandes et Git Bash, sauf mention contraire.
  • Le projet d'entraînement est créé dans C:\Users\simon\Desktop\Projets\junix-pulse-tuto, à côté du vrai projet, pour ne jamais l'abîmer.
  • Expo Go et la version du SDK. Expo Go n'ouvre que les projets d'une version précise d'Expo (le « SDK »). Au 12 novembre 2026, la documentation d'Expo indique : npx create-expo-app@latest sans option crée un projet SDK 57, la version qu'Expo Go accepte sur un vrai téléphone ; un projet SDK 58 (celui du vrai Junix Pulse) se crée avec --template default@sdk-58 mais ne s'ouvre pas dans Expo Go pendant la transition. On fait donc comme le vrai projet : on commence en SDK 57 avec Expo Go, et on passe au SDK 58 à la phase 15.
  • Expo Go suffit jusqu'à la phase 15. À partir de la phase 16, le projet utilise des modules natifs qu'Expo Go ne contient pas (chiffrement natif, widget, dictée) : on passe alors à un « build de développement » ou à l'APK.

// Le nom exact d'une icône Ionicons (TypeScript refusera un nom qui n'existe pas)
type IconName = keyof typeof Ionicons.glyphMap;

// Petite fonction qui fabrique l'icône d'un onglet : pleine et violette si actif, contour gris sinon
function tabIcon(filled: IconName, outline: IconName) {

// src/database/sqlite.ts — ouvre la base SQLite UNE fois et applique les migrations manquantes.
import * as SQLite from "expo-sqlite"; // la base de données dans le téléphone
import { MIGRATIONS } from "./migrations"; // notre liste de migrations

let dbInstance: SQLite.SQLiteDatabase | null = null; // la base, gardée après la 1re ouverture

export async function getDatabase(): Promise<SQLite.SQLiteDatabase> {
  if (dbInstance) return dbInstance; // déjà ouverte : on la réutilise

  const db = await SQLite.openDatabaseAsync("junix-pulse.db"); // crée le fichier s'il n'existe pas
  await db.execAsync("PRAGMA foreign_keys = ON;"); // SQLite ne vérifie les liens entre tables que si on le demande
  await db.execAsync("PRAGMA journal_mode = WAL;"); // mode plus rapide et plus sûr

  // La table qui retient quelles migrations ont déjà été appliquées
  await db.execAsync(
    "CREATE TABLE IF NOT EXISTS _migrations (version INTEGER PRIMARY KEY NOT NULL, name TEXT NOT NULL, applied_at TEXT NOT NULL);"
  );
  const applied = await db.getAllAsync<{ version: number }>("SELECT version FROM _migrations");
  const done = new Set(applied.map((row) => row.version)); // ex. {1, 2}

  for (const migration of MIGRATIONS) {
    if (done.has(migration.version)) continue; // déjà faite : on passe
    // Une transaction : soit TOUT réussit, soit RIEN n'est gardé (pas de base à moitié modifiée)
    await db.withTransactionAsync(async () => {
      await db.execAsync(migration.sql);
      await db.runAsync(
        "INSERT INTO _migrations (version, name, applied_at) VALUES (?, ?, ?)",
        migration.version,
        migration.name,
        new Date().toISOString()
      );
    });
  }

  dbInstance = db; // on la garde pour les prochains appels
  return db;
}

  label: string; // le texte du bouton

/** Les trois heures proposées : dans 1 h, ce soir 20 h (ou demain 20 h si c'est passé), demain 9 h. */
export function quickTimes(now: Date): QuickTime[] {
  const inOneHour = new Date(now.getTime() + 60 * 60 * 1000); // + 60 minutes en millisecondes

  const evening = new Date(now); // copie de « maintenant »
  evening.setHours(20, 0, 0, 0); // 20:00:00.000 le même jour
  if (evening <= now) evening.setDate(evening.getDate() + 1); // déjà passé : demain soir

  const tomorrowMorning = new Date(now);
  tomorrowMorning.setDate(tomorrowMorning.getDate() + 1); // demain
  tomorrowMorning.setHours(9, 0, 0, 0); // à 9:00

  return [
    { label: "Dans 1 h", date: inOneHour },
    { label: "Ce soir 20 h", date: evening },
    { label: "Demain 9 h", date: tomorrowMorning },
  ];
}
